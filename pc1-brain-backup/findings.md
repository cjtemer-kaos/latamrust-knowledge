## gemas_core v1.3.0 — rate_limiter (2026-06-05)

**Ported from** `pewdiepie-archdaemon/odysseus` (`src/rate_limiter.py`, 49 lines source, MIT).
Mirror: `D:\ias\proyectos\autopsia\odysseus\`.

### Decision
Top 3 from v1.2.0 (atomic_io, prompt_security, plan_mode) cleared a real gap in
crash-safe persistence, anti-injection, and plan gating. v1.3.0 picks the next
highest-value pattern from the same repo: **rate limiting**.

### Why
Neither `/api/chat` nor `/api/rust/rcon` in latamrust-nexus or supernexus-v2
have any rate limiting today. A misbehaving client (or attacker) can flood
the WebSocket RCON bridge, the Ollama dispatcher, or the chat handler with
no backpressure mechanism. The odysseus implementation is 49 lines of
sliding-window, key-based, thread-safe logic — a perfect first rate limiter.

### What landed

**`core/rate_limiter.py`** — `RateLimiter(max_requests, window_seconds)`:
- `check(key) -> bool` — sliding-window allow/deny. Denied requests are NOT
  timestamped (so a flood of denied requests can't extend the block window).
- `reset(key)` — clears one key (admin override / post-auth refresh / tests).
- `reset_all()` — clears everything.
- `snapshot() -> Dict[str, int]` — observability for admin dashboards.
- `_maybe_cleanup()` — inline background work, gated by
  `max(window * 2, 120)`. No thread to start, stop, or leak.
- `threading.Lock` guards the internal `Dict[str, List[float]]`.
- Validates `window_seconds > 0` (raises ValueError). `max_requests` is
  clamped to `>= 0` (negative = block everything).
- ~110 lines source (vs 49 in odysseus — the extras are `reset`/`reset_all`/
  `snapshot`, thread safety, edge-case validation, and the docstring/usage
  example).

**24 unit tests** in `tests/test_rate_limiter.py`:
- Basic allow/deny (incl. denied requests don't extend the block).
- Sliding window: full expiry, partial expiry, mixed timestamps.
- Per-key isolation, unknown-key behaviour.
- `reset` / `reset_all` semantics (single key, multi-key, unknown key).
- `snapshot` shape (counts, denied keys, empty limiter).
- Edge cases: max=0 (block all), max=1 (allow-then-block), max=-1 (clamped
  to 0), empty string key, window=0/-1 (raises ValueError).
- Concurrency: 50 threads racing for 10 slots on one key, 20 threads on
  distinct keys — lock prevents over-allowance.
- Cleanup: stale keys purged after `_cleanup_interval` elapses.

## gemas_core v1.4.0 — aiohttp rate-limit integration (2026-06-05)

**Builds on:** v1.3.0 `RateLimiter` (in-memory sliding-window).
**Ported from:** N/A — designed in-house to match the existing
latamrust-nexus aiohttp architecture (no upstream pattern in
odysseus/prompt-master/ruflo).

### Why v1.4.0

v1.3.0 shipped a generic, stdlib-only rate limiter. But the only way
to *use* it in aiohttp was to write the 429-by-hand boilerplate
yourself, every time. v1.4.0 closes that gap with a thin aiohttp
integration layer. The goal: the wiring is one or two lines, and
new endpoints get rate-limited by adding `check_http(...)` at the
top, not by re-implementing 429 + Retry-After + body shape every time.

### What landed

**`core/rate_limit_helpers.py`** — four helpers, lazy aiohttp import:
- `client_key(request, *, prefix="")` — extracts a stable key from
  `X-Forwarded-For` (leftmost hop) or `request.remote`. `prefix`
  lets callers namespace keys per route family.
- `check_http(limiter, key)` — returns a 429 `web.json_response`
  with `Retry-After` header if blocked, else `None`. Handlers
  short-circuit on non-`None`.
- `check_ws(limiter, ws, key)` — for WebSocket message loops.
  Sends `{"type": "error", "text": "rate limit exceeded"}` and
  closes with code 1008 if blocked, returns `True` if allowed.
- `rate_limit_middleware(limiter, *, key_fn=None)` — aiohttp
  middleware factory for blanket protection.

**17 unit tests** in `tests/test_rate_limit_helpers.py` (with mocked
aiohttp — no real server): client_key from remote / XFF / prefix;
check_http allow/deny/body/headers; check_ws allow/deny/error-frame/
close-code; middleware allow/deny/custom-key-fn.

**13 integration tests** in `latamrust-nexus/tests/test_v140_rate_limit.py`:
shared limiters defaults (60/30 per minute), check_http against real
aiohttp, check_ws against real WS, client_key with real request
shapes, middleware factory returns a callable.

**4 E2E smoke tests** in `temp/opencode/smoke_v140_rate_limit.py`:
real aiohttp test server, real ClientSession, real WS — exercises
the full stack: 3 allowed + 4th 429 with correct headers, per-IP
isolation via X-Forwarded-For, middleware variant, WS message gate
with proper close code 1008.

### Wire-up in `latamrust-nexus`

`src/api/rate_limiters.py` (new, 17 lines) — module that owns the
two shared `RateLimiter` instances. Lives in a separate module to
break the import cycle between `latamrust_server.py` and
`latamrust_routes.py`.

- `chat_limiter` — `RateLimiter(60, 60)` — 60 req / min per IP,
  shared bucket between `/api/chat` and `/api/chat/ask`.
- `rcon_limiter` — `RateLimiter(30, 60)` — 30 req / min per
  `(IP, server)`, more restrictive because each RCON request
  does 3 RTTs to the game server + IO in `data/rust/`.

`src/api/latamrust_server.py`:
- `POST /api/chat` — `denied = check_http(chat_limiter, client_key(request, prefix="chat"))`
- `POST /api/chat/ask` — same `chat_limiter`, same prefix.
- `GET /api/rust/rcon/ws` — per-message check inside the
  `async for msg in ws:` loop, key `rcon:<ip>:<server>`.
  Per-WS-connection, per-server, so one client can have
  several WS open to different servers with independent budgets.

`src/api/latamrust_routes.py`:
- `POST /api/rust/rcon` — body parsed *before* the limit check
  so the bucket reflects the actual server, not just the IP.

`src/api/server.py` (the fork, with `/api/rcon/*` namespace):
- `GET /api/rcon/servers` — `rcon_limiter` with prefix `rcon-fork:`
- `POST /api/rcon/command` — same prefix, key
  `rcon-fork:<ip>:<server>`. Prefix separates from the
  `latamrust_server.py` RCON namespace so the two don't
  share buckets.

### Why not `supernexus-v2` and `sfdx`?

Both already have a `backend.safety.check_rate_limit(client_ip)`
call at the top of `handle_chat` (a pre-existing safety module
that's not in gemas_core). Adding the new `RateLimiter` on top
would be duplicative. Replacing the safety module is a bigger
refactor than v1.4.0 — left for a future v1.5+ that unifies the
two rate-limit backends behind a single interface.
